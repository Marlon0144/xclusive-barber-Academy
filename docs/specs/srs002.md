## 1. Introduction

### 1.1 Document Purpose

Esta SRS documenta los hallazgos de la auditoría exhaustiva de deuda técnica
realizada sobre el repositorio `xclusive-barber-Academy` y la base de datos
Supabase `Academy-Xclusive-Barber-DB`. Define los requisitos verificables de
remediación que deben cumplirse **antes** de proceder a refactorizaciones de
flujo, arquitectura o diseño (Parte 2+ del PRD001).

**Audiencias principales:**
- **Marlon (Tech Lead / Desarrollador):** Aprueba el diagnóstico y ejecuta las
  correcciones en el orden priorizado.
- **El Ejecutor (Agente de Implementación):** Sigue los contratos y schemas aquí
  definidos para aplicar cada remediación sin ambigüedad.
- **QA / Verificación:** Usa la matriz de verificación (Sección 4) para validar
  cada corrección.

### 1.2 Product Scope

**Producto:** Xclusive Barber Academy — plataforma SaaS / CRM para academia de
barbería con gestión de lecciones, editor enriquecido (Tiptap), seguimiento de
estudiantes y módulo de evaluación automatizada con IA (OpenAI).

**Alcance de este documento (Parte 1):**
- **Incluye:** Diagnóstico de deuda técnica en base de datos Supabase, código
  fuente, build/dependencias, pruebas y documentación.
- **Excluye:** Refactorización de flujos de usuario, cambios de UI/UX, nuevas
  features, rebranding, optimización de diseño.

## 2. Product Overview

### 2.1 Product Perspective

Xclusive Barber Academy es una plataforma SaaS vertical para la gestión integral
de una academia de barbería. El sistema actual está en etapa **pre-MVP funcional**:
la arquitectura, autenticación, y la mayoría de flujos CRUD están implementados,
pero existen deudas técnicas que impiden un despliegue de producción robusto.

El sistema se compone de:
- **Frontend:** Next.js 15 (App Router) con React 19, Tailwind CSS v4, Shadcn/UI.
- **Backend:** Supabase (Auth, Postgres 17.6, Storage), Server Actions de Next.js.
- **IA:** OpenAI API para generación de feedback en evaluaciones de estudiantes.

**Contexto de esta auditoría:** El repositorio será transformado en un proyecto
de referencia ("well-structured, tested, rebranded, documented"). Esta Parte 1
establece la línea base de calidad antes de cualquier mejora.

### 2.2 Product Functions

Funcionalidades actualmente implementadas (sujetas a auditoría):

1. **Autenticación y Registro:** Login/logout con Supabase Auth. Registro mediante
   código de invitación (`/apply`, ruta legacy `/signup` coexiste).
2. **Dashboard Hub:** Panel principal con tarjetas de acceso filtradas por rol
   (`student`, `instructor`, `admin`).
3. **Gestión de Cursos:** CRUD de módulos y lecciones con editor enriquecido Tiptap
   (admin). Visualización de lecciones con reproductor de video YouTube (student).
4. **Tracker de Prácticas:** Subida de imágenes de cortes con validación de formato.
   Historial de submissions con eliminación.
5. **Evaluación (Grading):** Sliders 0-10 por criterio (fade, cleanliness,
   technique, symmetry) + feedback generado por IA (OpenAI).
6. **Progreso Profesional:** Dashboard RSC puro con 4 competencias y niveles
   derivados de lecciones completadas.
7. **CRM de Leads:** Captura de leads públicos, formulario de calificación,
   scoring automático, gestión admin.
8. **Landing Page:** 6 secciones RSC con formulario de captura de teléfono,
   precios, instructores.
9. **i18n ES/EN:** Selector de idioma con diccionarios para UI pública y dashboard
   (parcialmente completado — SRS001).
10. **Analytics:** Google Analytics 4, Google Tag Manager, Meta Pixel (opcionales).

### 2.3 Product Constraints

- **Stack obligatorio:** Next.js 15 (App Router), React 19, TypeScript strict,
  Tailwind CSS v4, Supabase (Auth + Postgres + Storage), Zod para validación,
  Server Actions para mutaciones.
- **Mobile-first:** Los estudiantes usan principalmente celular. Breakpoints
  base = mobile, `md:` = tablet, `lg:` = desktop.
- **Seguridad:** Toda mutación debe pasar por Server Action con patrón:
  auth → validate (Zod) → mutate → revalidate.
- **Performance:** React.cache() para deduplicar queries, dynamic import para
  librerías pesadas, Promise.all() para queries independientes.
- **Base de datos:** RLS obligatorio en todas las tablas con datos de usuario.
  Dual-client pattern (Normal vs Admin) para operaciones privilegiadas.

### 2.4 User Characteristics

| Rol | Descripción | Acceso |
|-----|-------------|--------|
| **Student** | Alumno de la academia. Ve cursos, sube prácticas, consulta progreso. | `/dashboard`, `/dashboard/courses`, `/dashboard/tracker`, `/dashboard/progreso_profesional` |
| **Instructor** | Profesor/evaluador. Mismas vistas que student + grading de submissions. | Todo lo de student + `/dashboard/grading` |
| **Admin** | Administrador del sistema. CRUD completo, gestión de usuarios, CRM. | Todo + `/dashboard/admin/*` |
| **Público (anon)** | Visitante sin autenticación. Ve landing, aplica, se califica como lead. | `/`, `/apply`, `/qualify`, `/login` |

### 3.2 Functional

- ID: REQ-SEC-001
- Title: Unificar criterio de autorización RLS — usar `profiles.role` en todas las políticas
- Statement: El sistema debe usar EXCLUSIVAMENTE `profiles.role` (consulta a tabla `profiles`) como fuente de verdad para autorización en RLS. Las políticas que actualmente usan `auth.jwt() -> 'app_metadata' -> 'role'` deben ser reemplazadas.
- Rationale: La inconsistencia actual genera un vector de seguridad: un atacante que manipule el JWT metadata podría eludir políticas en `modules` y `lessons` mientras que `submissions` y `crm_leads` usan el criterio correcto (`profiles.role`). Esto está documentado como deuda técnica #1 en AGENTS.md. La fuente de verdad única debe ser la base de datos.
- Acceptance Criteria:
  1. Las políticas RLS de `modules` (`Gestionar Modulos (Admin)`) y `lessons` (`Gestionar Lecciones (Admin)`) deben cambiarse de `auth.jwt() -> 'app_metadata' ->> 'role' = 'admin'` a `EXISTS (SELECT 1 FROM profiles WHERE profiles.id = auth.uid() AND profiles.role = 'admin')`.
  2. Ninguna política RLS en `public` debe usar `auth.jwt() -> 'app_metadata'` para decisiones de autorización.
  3. El admin client (`createAdminClient()`) debe seguir siendo el único mecanismo que bypass RLS.
- Verification Method: Analysis + Test

- ID: REQ-SEC-002
- Title: Habilitar protección de contraseñas filtradas (Leaked Password Protection)
- Statement: El sistema debe habilitar la funcionalidad "Leaked Password Protection" de Supabase Auth para prevenir el uso de contraseñas comprometidas (verificadas contra HaveIBeenPwned.org).
- Rationale: El advisor de seguridad de Supabase reporta esta protección como deshabilitada. Es una capa de defensa crítica contra credential stuffing.
- Acceptance Criteria:
  1. La protección debe estar habilitada en el dashboard de Supabase Auth → Settings → Password Strength.
  2. Al intentar registrar o cambiar una contraseña que aparece en HaveIBeenPwned.org, Supabase debe rechazarla con un error descriptivo.
- Verification Method: Demonstration

- ID: REQ-SEC-003
- Title: Agregar política UPDATE para la tabla `profiles`
- Statement: El sistema debe permitir que un usuario autenticado actualice su propio perfil (`full_name`, `avatar_url`) mediante una política RLS `WITH CHECK (auth.uid() = id)`.
- Rationale: Actualmente no existe ninguna política UPDATE en `profiles`. Si en el futuro se implementa edición de perfil, fallará silenciosamente o requerirá Admin client innecesariamente.
- Acceptance Criteria:
  1. Existe una política RLS `Users can update own profile` en `public.profiles` para `UPDATE` con `USING (auth.uid() = id)` y `WITH CHECK (auth.uid() = id)`.
  2. Un usuario autenticado puede modificar su `full_name` y `avatar_url` sin usar Admin client.
  3. Un usuario NO puede modificar el perfil de otro usuario.
- Verification Method: Test

- ID: REQ-FUNC-001
- Title: Agregar validación Zod en `app/signup/actions.ts` (o deprecar ruta)
- Statement: Si la ruta `/signup` se mantiene, su Server Action `signup()` debe validar inputs con Zod. Si se decide eliminar la ruta legacy, debe redirigir a `/apply` y el action debe ser eliminado.
- Rationale: `signup/actions.ts` usa `formData.get()` sin validación de tipos ni sanitización. AGENTS.md marca `/signup` como legacy (#3 en deuda técnica). La ruta activa es `/apply` cuyo action sí usa Zod.
- Acceptance Criteria:
  - **Opción A (deprecar):** La ruta `/signup` redirige 308 a `/apply`. El archivo `app/signup/actions.ts` se elimina. `middleware.ts` no referencia `/signup`.
  - **Opción B (mantener):** `signup()` usa `z.object({...})` para validar email, password, fullName, inviteCode. Retorna `SignupState` con errores tipados.
- Verification Method: Test + Inspection

- ID: REQ-FUNC-002
- Title: Agregar validación Zod en `app/login/actions.ts`
- Statement: El Server Action `login()` debe validar `email` y `password` con Zod antes de invocar `supabase.auth.signInWithPassword()`.
- Rationale: Actualmente extrae `formData.get('email')` y `formData.get('password')` sin validar. Aunque Supabase Auth rechaza credenciales inválidas, la falta de validación temprana impide mensajes de error UX adecuados (ej: "email inválido" vs "credenciales incorrectas").
- Acceptance Criteria:
  1. `login()` usa un schema Zod: `z.object({ email: z.string().email(), password: z.string().min(6) })`.
  2. Si la validación falla, retorna el error al cliente sin invocar Supabase Auth.
  3. Los mensajes de error usan i18n (`getServerDictionary()`).
- Verification Method: Test

- ID: REQ-FUNC-003
- Title: Agregar validación Zod en `app/dashboard/admin/gestion_users/actions.ts`
- Statement: Los Server Actions de gestión de usuarios (`createInvitation`, `deleteInvitation`, etc.) deben validar inputs con Zod en lugar de parseo manual de FormData.
- Rationale: Actualmente usa funciones manuales (`parseRole`, `parseMaxUses`) sin validación estructural. Zod proporcionaría validación declarativa, mensajes de error i18n, y tipos inferidos.
- Acceptance Criteria:
  1. Existe un schema Zod para creación de invitaciones: `z.object({ role: z.enum(['admin','instructor','student']), maxUses: z.number().int().min(1).max(50) })`.
  2. Existe un schema Zod para eliminación: `z.object({ invitationId: z.string().uuid() })`.
  3. Las funciones `parseRole()` y `parseMaxUses()` son eliminadas.
- Verification Method: Test + Inspection

- ID: REQ-FUNC-004
- Title: Agregar validación Zod en `app/dashboard/grading/actions.ts`
- Statement: El Server Action `submitGrade()` debe validar `submissionId` (UUID) y `grades` (4 números 0-10) con Zod.
- Rationale: Actualmente `grades` se recibe como `interface Grades` sin validación en runtime. Un cliente malicioso podría enviar valores negativos, strings, o campos adicionales.
- Acceptance Criteria:
  1. `submitGrade()` usa `z.object({ submissionId: z.string().uuid(), grades: z.object({ fade: z.number().min(0).max(10), cleanliness: z.number().min(0).max(10), technique: z.number().min(0).max(10), symmetry: z.number().min(0).max(10) }) })`.
  2. Si `submissionId` no es UUID válido, retorna error sin consultar BD.
  3. Si algún grade está fuera de rango [0,10], retorna error descriptivo.
- Verification Method: Test

- ID: REQ-FUNC-005
- Title: Resolver coexistencia de rutas `/signup` y `/apply`
- Statement: El sistema debe tener exactamente UNA ruta de registro. La ruta legacy `/signup` debe ser eliminada o redirigida permanentemente a `/apply`.
- Rationale: Dos rutas de registro generan confusión, duplicación de lógica, y superficie de ataque innecesaria. AGENTS.md documenta esto como deuda técnica #3.
- Acceptance Criteria:
  1. `middleware.ts` no referencia `/signup`.
  2. La carpeta `app/signup/` no existe O solo contiene un `page.tsx` que hace `permanentRedirect('/apply')`.
  3. `docs/ROUTES.md` refleja que `/apply` es la única ruta de registro.
- Verification Method: Inspection

### 3.3 Quality of Service

#### 3.3.2 Security

Los requisitos de seguridad están detallados en [3.2 Functional](#32-functional):

**Hallazgo adicional (informativo):**

#### 3.3.1 Performance

- ID: REQ-PERF-001
- Title: Agregar índices para claves foráneas no indexadas
- Statement: El sistema debe tener índices covering para todas las claves foráneas listadas por el advisor `unindexed_foreign_keys` de Supabase.
- Rationale: 7 FKs sin índice causan sequential scans en JOINs y degradación de performance a escala.
- Acceptance Criteria:
  1. Se crean índices B-tree en las siguientes columnas:
     - `crm_leads.reviewed_by`
     - `invitations.lead_id`
     - `lesson_progress.lesson_id`
     - `lesson_progress.verified_by`
     - `lessons.module_id`
     - `submissions.grader_id`
     - `submissions.student_id` (si no existe ya; verificar)
  2. El advisor `unindexed_foreign_keys` de Supabase reporta 0 hallazgos después de la migración.
- Verification Method: Analysis (Supabase advisor)

- ID: REQ-PERF-002
- Title: Optimizar políticas RLS con `(SELECT auth.uid())` en lugar de `auth.uid()`
- Statement: Todas las políticas RLS que usan `auth.uid()` deben reescribirse como `(SELECT auth.uid())` para que Postgres evalúe la función una sola vez (initPlan) en lugar de por cada fila.
- Rationale: El advisor `auth_rls_initplan` reporta 23 políticas que re-evalúan `auth.uid()` por fila. Esto causa degradación lineal con el número de filas.
- Acceptance Criteria:
  1. Las 23 políticas identificadas usan `(SELECT auth.uid())` en lugar de `auth.uid()`.
  2. El advisor `auth_rls_initplan` de Supabase reporta 0 hallazgos.
- Verification Method: Analysis (Supabase advisor)

- ID: REQ-PERF-003
- Title: Consolidar políticas RLS múltiples para misma acción y rol
- Statement: Las tablas con múltiples políticas permisivas para el mismo rol y acción deben consolidarse en una única política con condiciones combinadas mediante OR.
- Rationale: El advisor `multiple_permissive_policies` reporta 8 casos donde Postgres debe evaluar múltiples políticas para cada query. Esto es subóptimo: cada política adicional agrega overhead de evaluación.
- Acceptance Criteria:
  1. `crm_leads`: Las políticas `crm_leads_admin_select` y `crm_leads_owner_select` se consolidan en una única política `SELECT` con `(profile_id = auth.uid() OR EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'admin'))`.
  2. `lessons`: `Gestionar Lecciones (Admin)` + `Ver Lecciones (Todos)` → una política `SELECT` con `true` (todos los authenticated pueden ver lecciones) y separar write operations.
  3. `modules`: Similar a lessons.
  4. `submissions`: `Estudiantes ven sus practicas` + `Staff ve todo` → una política `SELECT` con la condición OR.
  5. El advisor `multiple_permissive_policies` reporta 0 hallazgos.
- Verification Method: Analysis (Supabase advisor)

- ID: REQ-PERF-004
- Title: Eliminar índices no utilizados
- Statement: Los índices `crm_leads_status_idx` y `crm_leads_created_at_idx` deben ser eliminados si tras análisis se confirma que no son necesarios para queries existentes.
- Rationale: El advisor `unused_index` reporta estos dos índices sin uso. Índices no utilizados consumen storage y ralentizan escrituras (INSERT/UPDATE/DELETE).
- Acceptance Criteria:
  1. Se verifica que ninguna query en el código fuente (Server Actions, cache-helpers) usa `status` o `created_at` en cláusulas WHERE/ORDER BY para `crm_leads`.
  2. Si no hay uso, los índices se eliminan mediante migración.
  3. Si hay uso (aunque no detectado por pg_stat_statements), se documenta la razón y se mantiene el índice.
- Verification Method: Analysis

No se detectaron hallazgos de disponibilidad. El proyecto Supabase está `ACTIVE_HEALTHY` y no tiene advisories de health.

### 3.5 Design and Implementation

#### 3.5.2 Build and Delivery

- ID: REQ-BUILD-001
- Title: Declarar `zod` como dependencia directa en `package.json`
- Statement: El paquete `zod` debe declararse explícitamente en `dependencies` de `package.json` con la versión `^4.3.0` (la versión realmente instalada y usada en el código).
- Rationale: `zod` es importado directamente en 7+ archivos del código fuente (`app/apply/actions.ts`, `app/dashboard/admin/courses/actions.ts`, `app/dashboard/admin/leads/actions.ts`, `app/dashboard/admin/lessons/[lessonId]/edit/actions.ts`, `app/dashboard/tracker/actions.ts`, `app/qualify/actions.ts`, `app/landing/actions.ts`) pero NO está en `package.json`. Es una phantom dependency que funciona solo porque `openai` y `eslint-config-next` lo instalan transitivamente. Si esos paquetes cambian su dependencia, el build romperá.
- Acceptance Criteria:
  1. `package.json` → `dependencies` incluye `"zod": "^4.3.0"`.
  2. `npm ls zod` muestra `zod` como dependencia directa del proyecto.
  3. `npm install` no produce warnings de dependencias phantom.
- Verification Method: Inspection

- ID: REQ-BUILD-002
- Title: Configurar Vitest como framework de testing
- Statement: El proyecto debe tener `vitest` declarado en `devDependencies`, un archivo de configuración (`vitest.config.ts`), y un script `"test"` en `package.json` que ejecute los tests existentes.
- Rationale: Existen 7 archivos de test en `tests/` que importan de `vitest`, pero `vitest` no está instalado ni configurado. Los tests no pueden ejecutarse. Esto es una phantom dependency de desarrollo y bloquea cualquier verificación automatizada.
- Acceptance Criteria:
  1. `package.json` → `devDependencies` incluye `"vitest": "^3.0.0"`.
  2. Existe `vitest.config.ts` en la raíz con resolución de alias `@/` → `./`.

- ID: REQ-DATA-001
- Title: Resolver columnas duplicadas de ordenamiento en `lessons` (`order_index` vs `position`)
- Statement: La tabla `lessons` tiene dos columnas con propósito aparentemente idéntico: `order_index` (integer/int4, nullable, default 0) y `position` (smallint/int2, nullable, default 0). Se debe consolidar en una única columna.
- Rationale: Dos columnas de ordenamiento generan ambigüedad: ¿cuál es la fuente de verdad? El código (`courses/actions.ts`) usa `reorderLessonsInModule()` que actualiza `order_index`. `position` parece ser un artefacto no utilizado.
- Acceptance Criteria:
  1. Se verifica mediante búsqueda en el código fuente (`grep -r "position" --include="*.ts" --include="*.tsx"`) que `position` no es referenciada en ninguna query o Server Action.
  2. Si no tiene uso, se elimina la columna `position` mediante migración.
  3. Si tiene uso, se unifica la lógica para usar solo `order_index` y se elimina `position`.
  4. `DATABASE.md` refleja una única columna de ordenamiento.
- Verification Method: Analysis + Inspection

- ID: REQ-DATA-002
- Title: Evaluar conversión de CHECK constraints textuales a ENUMs nativos
- Statement: Las columnas que usan `CHECK (column = ANY (ARRAY[...]))` deben evaluarse para conversión a tipos ENUM nativos de Postgres, lo que mejoraría performance de comparación y legibilidad del schema.
- Rationale: Actualmente `modules.competency` y `crm_leads.status` usan CHECK constraints con arrays de texto. Un ENUM nativo (`CREATE TYPE competency AS ENUM (...)`) es más eficiente en almacenamiento (4 bytes vs text variable) y validación.
- Acceptance Criteria:
  1. Se evalúa el impacto de migración (las tablas tienen 0 filas en modules/lessons; crm_leads tiene 3 filas).
  2. Se crean los tipos ENUM: `competency_type`, `lead_status_type`.
  3. Las columnas se alteran para usar los nuevos ENUMs.
  4. Los tipos TypeScript en `types/crm.ts` y `types/progress.ts` reflejan los ENUMs.
- Verification Method: Analysis
